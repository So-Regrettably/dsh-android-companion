# 架构

## 一条消息的完整旅程

你发一句「今天有点累」，到收到回复，中间经过这些地方：

```
① 手机QQ ──► 腾讯服务器 ──► NapCat（VPS Docker）
                                        │
                          ② OneBot 11 WebSocket
                                        │
③ 手机 dsh-onebot 插件 ──► 拼装成带边界标记的 prompt
                                        │
                          ④ DSH（proot 容器内，:38571）
                                        │
                            模型调用（DeepSeek API）
                                        │
⑤ 出站管线：清洗 → 分条 → 加停顿 ──► 发回 NapCat ──► QQ
```

每一步都可能出问题，所以每一步都有对应的观测点：

| 环节 | 失败表现 | 怎么查 |
|---|---|---|
| ① 登录态 | 完全不回消息 | `get_friend_msg_history` 真发一条 |
| ② WS 连接 | 日志刷 `ECONNREFUSED` / `ENETUNREACH` | 看是"服务端拒"还是"本机无路由" |
| ③ 插件 | 收到但没进模型 | `dsh-web.log` 里有没有 `followup` |
| ④ DSH | 有 `followup` 没 `turn/end` | 卡死看门狗 |
| ⑤ 出站 | 有 `turn/end` 但没收到 | 日志里 `final send failed` |

> **`isLogin: true` 不代表能发。** 实测遇到过状态字段说已登录、实际发出去返回 `retcode 1200`。唯一的验证方式是**真的发一条，看对方收到没**。

## 为什么是这个形状

### 决策一：跑在 proot 容器里，而不是 Termux

DSH 官方提供了完整的 Linux rootfs + Node 运行时。用 `proot` 能跑真正的 Ubuntu 用户态，apt / pip / glibc 全都是标准的，省掉大量"为什么 Termux 里编译不过"的问题。

代价是 proot 的性能损耗和内存开销（约 10~15%），对一台 8 核 7.4G 的手机来说可以接受。

### 决策二：中间隔一台 VPS

不直接让手机连 QQ，理由有三个：

1. **手机 IP 会变**。家里的 WiFi 是 DHCP，运营商随时回收，换一次就要重配一遍。
2. **手机在 NAT 后面**。想让 NapCat（在手机上）被外网连上，得打洞或者做端口映射。
3. **NapCat 需要一个稳定的长连接**。QQ 的登录态对 IP 变动敏感，频繁换 IP 容易触发风控。

所以：VPS 只跑 NapCat（负责和 QQ 通信），手机只跑 DSH（负责生产消息）。两侧都是**客户端**，都往中间那个固定地址连。任何一侧重启，另一侧只是重连，不用重新配置。

### 决策三：守护脚本放宿主机，不放容器内

容器内的进程随容器死。而容器随 App 进程死。

所以关键的自愈逻辑必须放在**容器外面**——Magisk 的 `service.d` 是 init 拉起的，和 App 的生命周期完全解耦。

这是整套方案里最重要的一个决定。它意味着：**App 界面显示"DSH 未运行"完全不影响服务**，因为界面读的是 App 自己的状态记录，而服务是 root 起的。

### 决策四：状态放文件，不放内存

容器会被杀、DSH 会重启、会话会轮换。任何"只存在内存里"的东西都会丢。

所以：提醒队列、发送队列、定时任务、预算账本、记忆、日记——全部落文件。守护进程负责扫文件，不负责持有状态。

```
/root/.dsh/
├── reminders/<到期unix秒>.txt   提醒（文件名是时间，正文一行）
├── outbox/pending/              待重发队列
├── media/onebot/                媒体 + 状态 + 审计
├── sessions/                    会话记录
├── cron/jobs/                   定时任务
└── last-backup.json             备份状态
```

好处：任意时刻 `kill -9` 掉任何进程，重启后状态还在。坏处：需要处理并发写，所以锁要有超时、写入要原子（临时文件 + `mv`）。

## 三处备份，互不依赖

数据只有一份，机器坏了就全没。所以做了三处，**每一处都不依赖另外两处**：

| 位置 | 谁在推 | 依赖条件 | 保留 |
|---|---|---|---|
| 电脑 | 电脑上的 PowerShell 定时拉 | 电脑开机 + adb 能连 | 7 份 |
| 云服务器 | 手机自己 ssh 推 | 手机有 WiFi | 7 份 |
| 手机本地 | 同上顺手拷一份 | 无 | 3 份 |

关键点：**云端那份是手机自己推的，不依赖电脑**。这样即使电脑一个月不开，云端仍然每天有一份。

三处用同一个 `sha256` 校验，两端比对一致才算成功。还原有 `-List` / `-DryRun` 两种演练模式。

> ⚠️ 只有手机本地那份是"零依赖"的，但它和原数据在同一台机器上——**手机丢了三处都没用**（云和电脑还有）。

## 失败模式

这套东西跑久了，会遇到的失败加起来就这几类：

| 类型 | 典型现象 | 处置 |
|---|---|---|
| **进程消失** | 端口没了 | `dsh-heal` 120 秒内拉起 |
| **进程活着但不干活** | 有输入无输出，CPU 空转 | 看门狗：日志 5 分钟不增长就重启 |
| **状态卡死** | 会话过大，请求挂起 | 换会话（先备份 `chat-sessions.json`） |
| **外部不可达** | QQ 掉登录 | 真发一条验证；`RestartNapCat` 重登 |
| **磁盘/内存耗尽** | 写入失败、随机崩溃 | 内存守护清娱乐 App；日志轮转；临时快照定期清 |
| **权限/标签错乱** | 报"文件不存在"但文件在 | 每小时一次属主 + SELinux 自愈 |

每种都有对应的自动化处置，但**都保留了人工接管的口子**（脚本、CLI、日志位置）。

## 一个反直觉的经验

**越是想让它稳定，越要让它容易重启。**

一开始的想法是"尽量别重启，重启会丢上下文"。于是给会话设了很长的 TTL，出问题也不重启，硬扛。

结果是反的：硬扛的阶段，崩一次就是灾难（会话 3.4MB，恢复要几 GB 堆，直接 OOM）；改成"每天固定换会话 + 出问题就重启"之后，反而稳了——因为每一步的代价都被限制住了。

所以现在的原则是：

- 会话**每天换**（05:00），不追求"永续"
- 进程**该杀就杀**，`dsh-heal` 20 秒能拉起来
- 备份**每天做**，不追求"实时同步"

**可恢复性 > 不中断。**
